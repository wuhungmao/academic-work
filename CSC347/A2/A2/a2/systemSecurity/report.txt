5) [2 Marks] Report on what the attacker could have done to leave fewer traces than they did in this attack. 
	What would you do to detect a compromise even in this case? 

	- clear command history
	   - before excuting any commands, run 'unset HISTFILE' to prevent bash from recording commands
	   - after the attack, execute both history -c and rm ~/.bash_history to earse all command evidence
	   - this would have hidden the stuff like id, whoami in logs
	
	- erase login and auth records
	   - clear /var/log/wtmp to remove sid's login entries (the last command 
	     wouldn't show sid logged in on Oct 9 at 14:38 and 14:45)
	   - clear /var/log/lastlog to hide last login information
	   - clear /var/log/syslog enries showing network interface changes and Tripwire execution
	   - you could also just remove any of the above but that might also be sus
	   - remove entries from /var/log/auth.log showing sid's session opened with uid=0, sudo commands
	     for ifconfig and dhclient
	   - honestly now thniking about it, maybe you should also just selectively edit all of this
	     since it'll be less sus if you keep the files but only small things change
	
	- restore original file timestamps
	   - after touching /bin/cat and /bin/ps, use touch -r /bin/ls /bin/cat to restore modification
	     times to match other system binaries
	   - makes timestamp modifications less obvious during manual inspection
	   - but this wouldn't fool tripwire (asked gpt) since it also checks file hashes, sizes, and inodes
	
	- tamper with tripwire database
	   - after modifying the system, run tripwire --init to rebuild the tripwire database with the
	     comprimised state as the new baseline
	   - future tripwire checks would cmpare against the comprimised baseline and show no violations
	
	- use stealthier attack Methods
	   - boot the server from a live CD/USB instead of removing the hard drive - leaves fewer forensic
	     traces since work is done in RAM
	   - use single user mode or recovery mode to bypass authentication without gening login logs
	   - install kernel level rootkit instead of touching obvios system binaries
	   - create backdoor accounts with lower UIDs or hidden in middle of /etc/passwd instead of 
	     modifying existing user sid to uid 0 (which is madly suspicious especialyl since these users are few)
	
	how to detect compromise:
	- file integrity monitoring
	   - tripwire successfully detceted the /bin/cat and /bin/ps modifications even though they were
	     just timestamp changes with touch commands
	   - tripwire checks multiple file attributes: hashes, size, permissions, inode numbers,
	     modification times especially even if attacker restores timestamps, hash changes would still be detected
	   - continue using automated tripwire with alerts sent to external monitoring system
	
	- immutable & remote logging
	   - use chattr +a on log files to make them append only which makes even root not able to delete or modify them,
	     only append new entries
	   - configure remote syslog server that receives logs in real time over encrypted channel and so attacker
	     with physical access to this server cannot delete logs stored on seperate secured logging server
	   - even if local logs are cleared, these remote logs wil keep evidence of sids logins, sudo
	     commands, and network changes and can't be accessed
	
	- protected tripwire database
	   - store tripwire database and policy files on read only mount or separate secured system again
	   - attacker cannot modify baseline database to hide their changes
	   - store hashes of critical system files (/etc/passwd, /etc/shadow) on
	     external trusted system for independent verification
	
	- behavioral/anomaly detection
	   - monitor system uptime for unexpected resets
	     our attack showed 3 reboots in 4 minutes 
	     (14:32, 14:34, 14:36) which is highly abnormal and should trigger automated security alerts
	   - detect unexpected shutdowns or power cycles through hardware monitoring or remote monitoring
	   - use linux auditd which logs all system calls at kernel level which is harder to tamper
	     with than regular log files and would recrod all file access and modifications
	   - monitor for privilege escalation events (new uid 0 accounts, sudo usage by users)
	
	- snapshot and vresion comparison
	   - regular VM snapshots allow comparison of current system state to good previous snapshots
	   - even if attacker clears all logs and fixes timestamps, filesystem differences would be visible
	   - automated snapshot diffing can detect unauthorized changes to /etc/passwd, /etc/shadow, etc.
	   - compare running system against offline backup to detect discrepancies
	
	- network and access monitoring
	   - monitor for network configuration changes (ex. sid brought up eth1 and ran dhclient at 14:43)
	   - alert on new SSH connections from unexpected IP addresses (sid connected from 192.168.10.1)
	   - monitor for unusual user account activity (sid account suddenly active after being dormant)
